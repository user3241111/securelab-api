
# Модель загроз SecureLab, ЛР 6

## Межі огляду

Мета огляду — перевірити захищеність навчального SecureLab API після виконання попередніх лабораторних робіт, визначити основні ризики та підготувати виправлення для ЛР №6.

| Елемент | Що зафіксовано |
|---|---|
| Версія та середовище | Початкова версія `v0.5.0`, commit `e554f1092c3abb451cda8ebf39af17f1e42ff60b`. Робоча гілка `lab/6-hardening-review`. Використовується .NET SDK 10.0.303, локальне середовище розробки та PostgreSQL у Docker Compose. |
| Компоненти в межах огляду | Браузерний клієнт `Client`, ASP.NET Core Minimal API, рівні `Presentation`, `Application`, `Data`, ASP.NET Core Identity, PostgreSQL, конфігурація та журнали застосунку. |
| Активи | Облікові записи користувачів, автентифікаційні cookie, інциденти та їхні власники, коментарі, історія зміни статусів, права доступу, журнали аудиту, параметри підключення до бази даних. |
| Суб'єкти | Анонімний відвідувач, автентифікований користувач, користувач із правами аналітика, локальний розробник. |
| Точки входу | HTTP-маршрути `/api/auth/*`, `/api/me`, `/api/incidents/*`, браузерний клієнт, файли конфігурації, змінні середовища та залежності проєкту. |
| Межі довіри | Browser → API, API → PostgreSQL, Repository → Build, Environment → Configuration. |
| Наявні механізми захисту | ASP.NET Core Identity, cookie authentication, авторизація маршрутів, перевірка прав доступу до інцидентів, серверна валідація окремих параметрів, обмеження дозволених полів оновлення, CORS, CSP, security headers та структуроване журналювання відмови в тріажі. |
| Виключення | Не проводиться перевірка реальної інфраструктури, зовнішніх серверів, мережевих пристроїв та продуктивного середовища. Огляд обмежений локальним навчальним проєктом. |

## Очікувані властивості на межах

| Межа | Очікувана властивість |
|---|---|
| Browser → API | Сервер не довіряє введеним даним. Для захищених операцій перевіряються автентифікація, авторизація та права доступу до конкретного ресурсу. Операції зміни стану з cookie authentication мають бути захищені від CSRF. |
| API → PostgreSQL | Доступ до даних виконується через контрольовані запити. Користувач не повинен отримувати або змінювати чужі записи без відповідних прав. |
| Repository → Build | До репозиторію не повинні потрапляти реальні паролі, токени та інші секрети. Залежності й зміни коду мають бути контрольованими. |
| Environment → Configuration | Параметри конфігурації повинні відповідати середовищу запуску. Секрети продуктивного середовища не повинні зберігатися у відкритому вигляді в репозиторії. |

## Підтверджені механізми захисту

1. **Автентифікація.** У `Scaffolding/Lab03Identity.cs` використовується ASP.NET Core Identity з cookie authentication. Cookie має `HttpOnly=true` та `SameSite=Lax`. Поза Development використовується `SecurePolicy=Always`.

2. **Авторизація.** У `Presentation/Endpoints/IncidentEndpoints.cs` маршрути інцидентів вимагають автентифікації. Для окремих операцій додатково використовуються `CanRead`, `CanUpdate` та `CanDelete`.

3. **Контроль тріажу.** У `Presentation/Endpoints/IncidentTriageEndpoints.cs` перевіряється право `CanTriage`. Дозволений лише перехід статусу `New → Triaged`.

4. **Валідація.** Параметр `status` перевіряється через `Enum.TryParse` та `Enum.IsDefined`. Під час оновлення інциденту дозволено змінювати тільки `Title` і `Description`.

5. **HTTP-захист.** У `Program.cs` налаштовано CORS, Content-Security-Policy, `X-Content-Type-Options`, `Referrer-Policy` та `X-Frame-Options`.

6. **Аудит.** У `IncidentTriageEndpoints.cs` відмова в авторизації записується у структурований журнал із зазначенням користувача, ресурсу, дії, часу та `TraceId`.

## Виявлені ризики та обмеження

Основний ризик для подальшого виправлення — відсутність підтвердженої перевірки antiforgery-токенів на маршрутах, які змінюють дані та використовують cookie authentication.

Наявне налаштування `SameSite=Lax` зменшує ризик окремих CSRF-атак, але не є повною заміною antiforgery-захисту.

Маршрут `POST /api/auth/logout` наразі повертає HTTP 501, оскільки функцію виходу ще не реалізовано.

Інші можливі проблеми, зокрема наявність секретів у репозиторії, потребують окремої перевірки під час security review.
