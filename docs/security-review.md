## 1. Executive summary

У межах лабораторної роботи №6 проведено перевірку захищеності SecureLab API, зокрема автентифікації, авторизації, CSRF-захисту, обробки помилок, HTTP-заголовків безпеки та конфігурації застосунку.

Задокументовано дві знахідки: F-01 — використання навчальних облікових даних PostgreSQL у відстежуваних конфігураційних файлах, F-02 — відсутність CSRF-захисту на окремих операціях зміни стану.

F-01 прийнято як обмежений ризик локального навчального середовища (Accepted, study-only). Ознак компрометації реальних облікових даних у межах цієї перевірки не встановлено. F-02 виправлено та повторно перевірено.

Додатково реалізовано logout із CSRF-захистом, перевірено безпечну обробку HTTP 500 та заголовки безпеки. Останній запуск автоматизованих тестів завершився успішно: 21 тест пройдено, 0 помилок.

Залишаються обмеження щодо HTTPS/HSTS, login rate limiting, повного браузерного тестування та окремих негативних сценаріїв.

## 2. Scope та exclusions

До перевірки включено локальний застосунок SecureLab API, його HTTP endpoints, cookie-based authentication, правила авторизації, браузерний JavaScript-клієнт, поточні файли конфігурації та інтеграційні тести.

Основна увага приділялася поточному стану проєкту в Git. Повний аудит історії репозиторію, зовнішній penetration test, аналіз усіх сторонніх залежностей і перевірка розподіленої інфраструктури не виконувалися.

Перевірка проводилася в локальному тестовому середовищі.

## 3. System overview і trust boundaries

SecureLab API — вебзастосунок на ASP.NET Core із PostgreSQL, що забезпечує створення, перегляд, зміну та обробку інцидентів.

Основні компоненти: браузерний клієнт, HTTP API, система автентифікації ASP.NET Core Identity, механізми авторизації, Entity Framework Core і PostgreSQL.

Основні межі довіри проходять між браузером та API, автентифікованим користувачем і захищеними операціями, а також між застосунком і базою даних.

Детальніший опис активів, точок входу, меж довіри та загроз наведено у `docs/threat-model.md`.

## 6. Detailed findings

**F-01 — Навчальні облікові дані PostgreSQL у конфігурації.**

У трьох відстежуваних файлах конфігурації виявлено навчальні credentials PostgreSQL, передбачені baseline SecureLab: `infra/compose.yaml`, `appsettings.Development.json` та `SecureLabDesignTimeDbContextFactory.cs`.

Docker Compose налаштований публікувати порт PostgreSQL лише через `127.0.0.1:54329`.

Ризик класифіковано як Accepted (study-only), P3. Це не підтверджений витік реальних production credentials. Конфігурацію не змінювали; використання навчальних credentials поза локальним стендом не допускається.

У `.gitignore` передбачено виключення локальних файлів із секретами, зокрема `.env` та `appsettings.Local.json`. Це не змінює статусу трьох наявних відстежуваних файлів.

Деталі: `docs/findings/F-01-short-name.md`.

**F-02 — Недостатній CSRF-захист операцій зміни стану.**

Було виявлено, що окремі операції API, які використовують cookie-based authentication, не мали явної перевірки CSRF-токена.

Для виправлення додано antiforgery services і middleware, endpoint `/api/antiforgery/token`, фільтр `CsrfEndpointFilter.ValidateAsync` та підтримку передавання заголовка `X-CSRF-TOKEN` у відповідному браузерному клієнті.

Автентифікований POST `/api/incidents` без токена повернув HTTP 400, без створення нового запису. Запит із чинним токеном повернув HTTP 201 і створив інцидент.

Для logout додатково реалізовано `SignOutAsync()`, перевірку авторизації та CSRF-фільтр. Позитивна і негативна HTTP-перевірки завершилися успішно.

Статус F-02 — Fixed для реалізованого захисту та перевірених сценаріїв. Повний browser end-to-end retest усіх операцій не проводився.

Деталі: `docs/findings/F-02-csrf.md`.

### CP-01 — Production error handling

Для перевірки обробки помилок застосунок запускали в локальному Production-профілі з недоступним портом PostgreSQL.

Запит автентифікації спричинив HTTP 500. Клієнт отримав безпечну відповідь ProblemDetails із `traceId`, без розкриття внутрішнього stack trace та деталей підключення до БД.

Внутрішній журнал застосунку містив відповідний запис про виняток. Таким чином, клієнтська відповідь та серверне журналювання були розділені.

Після перевірки відновлено штатне підключення до БД. `/health` повернув HTTP 200.

### CP-02 — Security response headers

У `Program.cs` реалізовано встановлення чотирьох захисних HTTP-заголовків:

- `X-Content-Type-Options: nosniff`
- `Referrer-Policy: no-referrer`
- `X-Frame-Options: DENY`
- `Content-Security-Policy` з обмеженням джерел ресурсів, зокрема `default-src 'self'`, `object-src 'none'` та `frame-ancestors 'none'`.

Перевірено такі класи відповідей:

| HTTP | Сценарій | Результат |
|---|---|---|
| 200 | Статичний ресурс `/auth-lab.html` | PASS |
| 200 | API `/health` | PASS |
| 400 | Некоректний параметр `sortBy` | PASS |
| 404 | `/openapi/v1.json` у Production | PASS |
| 500 | Контрольована помилка підключення до БД | PASS |

Під час перевірки HTTP 500 було виявлено, що стандартний exception handler може очищати попередньо встановлені заголовки відповіді. Для виправлення використано `Response.OnStarting(...)`.

Після зміни повторний тест підтвердив наявність чотирьох заголовків також на HTTP 500.

### REG-CSRF-01 — перевірка відмов і дозволених операцій

Автентифікований POST `/api/incidents` без CSRF-токена повернув HTTP 400; під час ручної перевірки підтверджено відсутність нового запису. Запит із чинним CSRF-токеном повернув HTTP 201 і створив інцидент.

Інтеграційні тести використовують `SendWithCsrfAsync()` для PUT, DELETE і triage. Перевірено відмови HTTP 400/403 для недозволених операцій.

Для triage підтверджено незмінність статусу `New` після HTTP 403 та перехід `New` → `Triaged` після HTTP 204.

Окремі негативні CSRF-тести без токена для PUT, DELETE і triage, а також повний browser UI smoke не виконувалися. Це обмеження перевірки, а не підтверджений успішний тест.

### Login, logout, CSRF та авторизація — ручна регресія ЛР6

- Login: HTTP 204 — PASS.
- Авторизований GET `/api/me`: HTTP 200 — PASS.
- Logout із CSRF-токеном: HTTP 204 — PASS.
- GET `/api/me` після logout: HTTP 401 — PASS.
- Logout без CSRF-токена: HTTP 400 — PASS.
- GET `/api/me` після відхиленого logout: HTTP 200 — PASS.
- Автоматизована регресія після змін: 21/21 тестів успішно, 0 помилок — PASS.

Перевірки logout виконано через HTTP-запити у Development. Повний browser UI smoke не проводився.

### REG-XSS-01 — обмежена регресійна перевірка DOM-рендерингу

У браузерній консолі перевірено використання `textContent` для двох значень: XSS-маркера `<img src=x onerror=alert("XSS")>` та звичайного складного тексту з українськими літерами, спеціальними символами, лапками, перенесенням рядка й emoji.

Для обох значень підтверджено:

- точне збереження текстового значення;
- відсутність створених HTML-елементів;
- відсутність створеного `img` або `script` у тестовому DOM-вузлі.

Усі шість перевірок завершилися успішно.

Окремо автоматизований тест `ClientScript_DoesNotUseDangerousInnerHtmlSink` підтверджує відсутність `innerHTML` та використання `textContent` у перевіреному `wwwroot/auth-lab.js`.

**Обмеження:** консольний тест використовував ізольовану функцію рендерингу, а не повний сценарій завантаження збереженого payload із PostgreSQL через API та реальний інтерфейс. Тому повний Stored XSS regression після ЛР6 не вважається підтвердженим.

## 9. Remaining gaps and limitations

Незважаючи на успішні перевірки, залишаються такі обмеження:

- Production HTTPS/TLS та HSTS не підтверджено.
- Login rate limiting не підтверджено.
- Повний browser UI smoke після CSRF-змін не виконано.
- Після додавання CSRF-захисту до logout клієнтський виклик logout потребує окремої перевірки та, за необхідності, передавання токена.
- Не виконано окремі негативні CSRF-тести для PUT, DELETE і triage.
- Повний Stored XSS regression із даними з БД не виконано.
- SQLi перевірено лише трьома ручними HTTP-запитами.
- Повний аудит Git history та сторонніх залежностей не проводився.

Ці обмеження не змінюють фактичних результатів успішно виконаних тестів, але не дозволяють поширювати їх на неперевірені сценарії.

## 10. Conclusion

У лабораторній роботі №6 проведено security review SecureLab API, задокументовано findings F-01 і F-02, реалізовано CSRF-захист для перевірених операцій, безпечний logout, захисні HTTP-заголовки та обробку Production-помилок.

F-01 залишено в статусі Accepted (study-only), F-02 — Fixed. Перевірки HTTP 500, security headers, login/logout та відповідних сценаріїв авторизації завершилися успішно.

Останній запуск інтеграційних тестів: 21/21 PASS, 0 помилок.

Результати обмежуються перевіреними сценаріями локального середовища. Непідтверджені вимоги й залишкові ризики наведено окремо, без позначення їх як PASS.
