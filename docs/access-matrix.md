
# Матриця контролю доступу — ЛР №4

## 1. Загальні положення

Матриця визначає правила авторизації для SecureLab API за сценарієм baseline 2-A.

Основний ресурс — `Incident`. Власник визначається полем `Incident.OwnerUserId`. Дочірній ресурс — `IncidentComment`.

Ролі:
- Reporter — створює інциденти, переглядає та редагує власні записи.
- Analyst — переглядає інциденти для аналізу та виконує перехід New → Triaged.
- Administrator — має лише явно визначені адміністративні права, без автоматичного доступу до інцидентів.

Рішення про доступ ухвалюється сервером на основі перевіреного principal, ролі користувача, власника ресурсу та контексту операції.

## 2. Матриця контролю доступу

| Дія | Анонім | Reporter | Analyst | Administrator | Власник має значення? | Стан реалізації |
|---|---|---|---|---|---|---|
| GET /api/incidents — список | Deny, 401 | Allow, лише власні | Allow, усі для аналізу | Deny, 403 | Так, для Reporter | Реалізувати; A-05 |
| GET /api/incidents/{id} — деталі | Deny, 401 | Власний — 200; чужий — 403 | Allow, 200 | Deny, 403 | Так, для Reporter | Реалізувати; A-01, A-02, A-03, A-03R |
| POST /api/incidents — створення | Deny, 401 | Allow, для себе | Allow, для себе | Deny, 403 | Власника призначає сервер | Успадкований baseline ЛР 3; перевірити |
| PUT /api/incidents/{id} — оновлення вмісту | Deny, 401 | Власний — 204; чужий — 403 | Deny, 403 | Deny, 403 | Так | Реалізувати; A-04, A-08b |
| DELETE /api/incidents/{id} — видалення | Deny, 401 | Deny, 403 | Deny, 403 | Deny, 403 | Ні, дія заборонена | Реалізувати явну відмову; A-04 |
| POST /api/incidents/{id}/triage | Deny, 401 | Deny, 403 | Allow, 204 лише для New → Triaged; інакше 409 | Deny, 403 | Ні, важливі роль і поточний стан | Реалізувати; A-06, A-07, A-09 |
| GET /api/incident-comments/{id} — звичайний коментар | Deny, 401 | Власний incident — 200; чужий — 403 | Allow після перевірки parent | Deny, 403 | Так, для Reporter | Реалізувати; A-12 |
| GET /api/incident-comments/{id} — internal comment | Deny, 401 | Deny, 403 навіть для власного incident | Allow після перевірки parent | Deny, 403 | Самого володіння недостатньо | Реалізувати; A-12 |

Для неіснуючого ресурсу повертається HTTP 404.

Право Analyst переглядати інцидент не дозволяє редагувати його вміст або видаляти.

Видалення заборонено для всіх ролей, оскільки предметний контракт не надає явного дозволу на цю операцію.

## 3. Політика HTTP-відмов

Обрано політику HTTP 403 Forbidden для чужого наявного ресурсу.

- 401 Unauthorized — немає автентифікації.
- 403 Forbidden — користувач автентифікований, але не має необхідного права.
- 404 Not Found — ресурс не існує.
- 409 Conflict — поточний стан інциденту не дозволяє виконати triage.

Політика 403 застосовується до details, update, delete та child resource.

Перевага політики — явне розмежування відсутнього ресурсу та заборони доступу. Недолік — можливе підтвердження існування чужого ресурсу.

Тест A-10 не застосовується, оскільки обрано політику 403, а не 404.

## 4. Захист дочірніх ресурсів

Для доступу до `IncidentComment` сервер повинен перевірити:

1. Існування коментаря та пов'язаного інциденту.
2. Автентифіковану особу та роль із server-issued principal.
3. Право перегляду батьківського інциденту.
4. Властивість `IsInternal`.

Reporter не може переглядати internal comment навіть власного інциденту.

Analyst може переглядати internal comment після перевірки права доступу до батьківського інциденту.

Ті самі правила використовуються у details-проєкції та в GET /api/incident-comments/{id}.

## 5. Захист серверних полів

Поля `OwnerUserId`, `Id`, `Status`, role та службові часові мітки не можуть змінюватися через звичайний update.

Дозволені поля звичайного оновлення:
- Title;
- Description.

Обрано контракт A-08b: запит із забороненими або невідомими полями відхиляється з HTTP 400 Bad Request без зміни стану ресурсу.

Статус змінюється лише через окрему операцію triage. Сервер перевіряє статус New та сам встановлює Triaged.

## 6. Аудит відхилених привілейованих операцій

Для відхиленого POST /api/incidents/{id}/triage створюється структурована подія `authorization.denied`.

Подія містить:
- перевірений ідентифікатор користувача;
- назву операції;
- ідентифікатор ресурсу;
- результат denied;
- час UTC;
- traceId відповідного HTTP-запиту.

Паролі, cookie, токени, повне тіло запиту та конфіденційні дані інциденту не записуються.

## 7. Межі виконання

Матриця підготовлена для рівня «Добре».

Перевірки A-11 для search та severity-summary належать до рівня «Відмінно» і не включені до обсягу роботи.

Усі правила є цільовою політикою. Фактичні результати реалізації будуть підтверджені автоматизованими тестами та HTTP-перевірками.
